# Rust のライフタイムの基礎（ダングリング参照から `'_` まで）

日付: 2026-07-28

Bevy の `Mut<'w, T>` の `'w` が何を意味するのかを理解するために、ミニマムな Rust コードで
段階的に検証した内容をまとめる。ダングリング参照の禁止・構造体が参照を持つ場合の注釈・`'_`
の意味・そして「本物の `&mut T`」と「参照を持つ独自ラッパー構造体」とで暗黙 reborrow の効き方が
違うという検証まで、Bevy に限らない一般的な Rust の知識として整理する。

前提知識:
- `match` における参照越しの束縛（`&T` を分解すると中身も参照になる、という関連する挙動） →
  [[20260725_rust-match-and-pattern-binding]]

---

## 1. ダングリング参照（`E0597`）

ブロックを抜けた後もその中の変数への参照を持ち続けようとするとコンパイルエラーになる:

```rust
fn main() {
    let r;
    {
        let x = 5;
        r = &x;
    } // x はここで drop される
    println!("{r}"); // error[E0597]: `x` does not live long enough
}
```

参照は「参照先が生きている間しか有効でない」という制約をコンパイラが常に検査しており、
これが崩れる書き方は借用チェッカーがコンパイル時に弾く。ライフタイムの仕組みは、この制約を
型システムの中で表現し、実行前（コンパイル時）に違反を検出するためにある。

## 2. 参照をフィールドに持つ構造体はライフタイム注釈が要る（`E0106`）

```rust
struct Wrapper<T> {
    value: &T, // error[E0106]: missing lifetime specifier
}
```

構造体が参照をフィールドに持つ場合、その参照が「いつまで有効か」をコンパイラに伝える枠が
必要になる。`<>` にライフタイムパラメータを追加して解決する:

```rust
struct Wrapper<'a, T> {
    value: &'a T,
}
```

これは「`Wrapper<'a, T>` のインスタンスは、少なくとも `'a` の間だけ生きられる（＝ `value` の
参照先より長生きしない）」という制約を型に刻んでいる。

## 3. Bevy の `Mut<'w, T>` は `Wrapper<'a, T>` と構造的に同じ

Bevy の `Mut<'w, T>` は概念上 `value: &'w mut T` を持つ構造体（実際には内部で変更検知フラグも
併せ持つが、ライフタイムの持ち方という観点では 2 節の `Wrapper<'a, T>` と全く同じ形）。
`&'w mut T` という参照をフィールドに持つ以上、`Wrapper` と同じ理屈でライフタイムパラメータ
`'w` を型に持たなければならない。これが、クエリから `&mut Transform` を取り出したときの型が
`Mut<'_, Transform>`（＝ `Mut<'w, Transform>` の `'w` を省略表記したもの）になる理由。

## 4. `'_` は「枠は要るが名前は付けない」プレースホルダー

`Mut<'_, Transform>` の `'_` は、ライフタイムパラメータの枠は必要だが具体的な名前を書かず
コンパイラの推論に任せる、というプレースホルダー。`impl SomeTrait for Mut<'_, Transform>`
のように書けば、任意のライフタイム `'w` に対して impl を成立させられる（特定の `'w` に固定
しない）。

## 5. 素の `&mut T` と独自ラッパー `Mut<T>` の違い（暗黙 reborrow の範囲）

本物の `&mut T` は、ジェネリックな引数位置（`&C` のような境界）に暗黙の reborrow で渡せる。
一方 `Mut<T>` のような独自ラッパー構造体は、この「言語組み込みの暗黙変換」の対象にならない。
これをミニマムな例で確認した:

```rust
fn takes_ref<C>(_c: &C) {}

fn main() {
    let mut x = 5;
    let r: &mut i32 = &mut x;
    takes_ref(r); // OK: &mut i32 は暗黙の reborrow で &i32 相当として渡せる（実際は &&mut i32 だが、
                  // フィールドアクセス等の場面では deref coercion がよく効く）

    struct Wrapper<'a>(&'a mut i32);
    let w = Wrapper(&mut x);
    // takes_ref(w) は Wrapper に Deref を実装していない限り、
    // takes_ref が要求する型に暗黙変換されない
}
```

この非対称性が実務上ハマりやすいポイント。素の `&T`/`&mut T` はジェネリック関数にそのまま渡って
トレイト実装（`impl for T`）に自動でたどり着くが、`Mut<T>` のような独自ラッパーは同じ暗黙変換を
受けられないため、ラッパー型に対する impl を明示的に別途書く必要が出てくる。実際に Bevy の
`Mut<'_, Transform>` でこの問題に当たった具体例は
[[20260728_mut-transform-and-collision-module-split]] を参照。

## 6. まとめ

- 参照は「参照先が生きている間しか有効でない」という制約を持ち、これが崩れる書き方は
  借用チェッカー（`E0597` など）がコンパイル時に弾く。
- 構造体が参照をフィールドに持つ場合、`E0106` を避けるためにライフタイムパラメータ（`<'a>`）を
  型に持たせる必要がある。Bevy の `Mut<'w, T>` もこの形の一種。
- `'_` は「枠は要るが名前は付けない」プレースホルダーで、任意のライフタイムに対して impl を
  成立させたいときに使う。
- 本物の `&mut T` はジェネリック境界へ暗黙 reborrow できるが、独自ラッパー構造体（`Mut<T>` 相当）
  はこの暗黙変換の対象にならない。ラッパー型を汎用関数に渡したい場合は、そのラッパー型専用の
  impl を明示的に用意する必要がある。
