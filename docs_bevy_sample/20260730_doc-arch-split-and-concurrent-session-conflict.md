# doc_arch/ 設計書のテーマ別分割と、並行編集セッションとの競合対応

日付: 2026-07-30

`doc_arch/web-publish-and-ugc-architecture.md`（Web公開・UGC基盤の設計書、427行の単一ファイル）
をテーマ別に分割した作業の記録。分割自体は単純作業だが、途中で**別セッションによる並行編集**が
発覚し、対応方針の判断が必要になった。その経緯と教訓を残す。

関連: [[20260730_web-publish-and-ugc-architecture]]（分割前スナップショットのコピー。本ファイルとは別物）

---

## 1. 経緯

### 1.1 最初の分割案

ユーザーから「テーマ別にファイル分割したい」と依頼を受け、最初は以下の6領域で合意した。

- Overview
- Frontend
- Backend
- 機能要件
- Deploy（ローカル開発含む）
- Hosting・CI/CD

このとき、当初「フロントエンド変更点」という切り口で書きかけたが、指摘を受けて
**「フロントエンド全体」という粒度に修正した。**

> 設計ドキュメントは差分・変更点の羅列ではなく、そのドメイン全体の設計として記述すべき。
> 「変更点」という切り口は Pull Request の説明文には適しているが、後から読む人が
> 全体像を把握するための設計書には向かない。

### 1.2 並行編集の発覚

分割作業の途中、`doc_arch/web-publish-and-ugc-architecture.md` を読み直したところ、
**自分が最初に読み込んだ時点からファイルのタイムスタンプ・サイズが変わっている**ことに気づいた。
調査した結果、別の（おそらく並行して動作している）Claude Codeセッションが同じファイルを
リアルタイムで編集していたことが判明した。具体的な差分:

- `doc_arch/private/`（`.gitignore` で全除外設定された個人用ラフ案フォルダ）が新規作成され、
  `initial_idea.md` が置かれていた。
- 本体ファイルに、バックエンドを Supabase に確定させる記述が追記されていた。
- 新規の「Auth.js検討」セクション（§5.4 相当）が追記されていた。
- 機能要件を `doc_arch/requirements.md` へ分離する方針が既に書き込まれていた。

### 1.3 対応

- **古い内容を元にした分割案でそのまま `Write` で上書きすることはしなかった。** Edit ツールは
  「読み込み後にファイルが変更されているとエラーになる」仕組みを持つため、これに気づいた時点で
  作業を止めた。
- ユーザーに状況をそのまま報告し、進め方を確認した（黙って上書きしない）。
- ユーザー確認の上、**ファイルを最新内容で読み直してから分割をやり直した。**

## 2. 最終的な分割構成

並行セッションが既に `doc_arch/requirements.md` という**サブフォルダを介さないフラットなパス**を
参照していたため、それに整合性を合わせ、`doc_arch/` 直下にフラットに配置した（サブフォルダは
作らなかった）。

| ファイル | 内容 |
|---|---|
| `doc_arch/overview.md` | 目的・スコープ、As-Is/To-Be、段階的ロードマップ、アーキテクチャ側の未決事項 |
| `doc_arch/requirements.md` | 機能要件、要件側の未決事項 |
| `doc_arch/frontend.md` | フロントエンド全体の責務・画面構成・認証・クライアント側検証 |
| `doc_arch/backend.md` | バックエンド選定・ポータビリティ方針・Auth.js検討・データモデル・API設計・セキュリティ |
| `doc_arch/deploy.md` | ローカル開発環境（Docker Compose） |
| `doc_arch/hosting-and-cicd.md` | 本番ホスティング・CI/CD |

元の `doc_arch/web-publish-and-ugc-architecture.md` は、本文を残さず**上記6ファイルへのリンクのみの
索引**に置き換えた。

```markdown
# ブロック崩し Web 公開 & UGC 基盤 設計書

この設計書はテーマ別に分割されている。以下から個別の設計を参照すること。

- [全体概要](./overview.md) — ...
- [機能要件](./requirements.md)
- [フロントエンド設計](./frontend.md)
- [バックエンド設計](./backend.md) — ...
- [ローカル開発環境（デプロイ）](./deploy.md)
- [ホスティング・CI/CD](./hosting-and-cicd.md)
```

**内容を重複して残さなかった理由**: 索引ファイルに本文の要約やコピーを残すと、個別ファイル側だけ
更新されて索引側が古いままになる「ドリフト」が起きる。実際に今回、並行編集によって本体と
自分の作業コピーの間でまさにこの種の食い違いが発生し、混乱を招いた。同じ失敗を索引と個別ファイルの
間で再現させないため、索引は本当にリンクだけに絞った。

`doc_arch/private/`（gitignore済みの個人用メモ）には一切触れず、中身も読まなかった。
「private」と明示されたディレクトリ・ファイルは覗かない、という判断。

## 3. 教訓（一般化）

1. **複数セッション・並行編集が起きうる環境では、`Write` で対象ファイル全体を書き換える前に、
   タイムスタンプ・サイズなど「自分が読み込んだ時点から変わっていないか」を確認する。**
   `Edit` ツールは仕組み上これを検知してエラーにしてくれることがあるので、そのエラーを
   「バグ」ではなく「異常検知」として扱い、無理に回避せず最新内容を読み直す。
2. 古い内容を前提にした変更で上書きしそうになったら、**黙って修正するのではなく、ユーザーに
   状況を報告して進め方を確認する。** 特に「他セッションが編集していた」という事実はユーザー自身も
   把握していない可能性があるため、共有する価値が高い。
3. **設計書を分割・整理する際、索引ページには本文を重複させずリンクのみに絞る。** 重複した内容は
   将来ドリフトする前提で設計する。
4. ディレクトリ構成を決める際、既に他の作業（他セッションを含む）が特定のパス（今回は
   `doc_arch/requirements.md` のフラット配置）を前提に動いている場合は、後から来た側がそれに
   合わせて整合性を取る。
5. `private` と明示された領域には触れない。
