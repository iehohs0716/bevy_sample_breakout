# ゲームシナリオ／ゲームのデータモデルと、Supabase + DynamoDB ハイブリッド構成の決定

日付: 2026-07-30

UGC基盤の設計議論の中で、ゲームシナリオ・ゲームのデータモデルをクラス図で明確化し、
その保存先を「Supabase一本」から「Supabase + DynamoDB のハイブリッド」に確定させた経緯の記録。

関連: [[20260730_doc-arch-split-and-concurrent-session-conflict]] /
[[20260730_dynamodb-schema-as-design-doc-json-schema]]

---

## 1. 出発点：クラス図で提示されたデータモデル

ユーザーが draw.io で作成したクラス図（画像、後に mxGraphModel XML でも共有）をもとに、
以下の構造が明確になった。

- **ゲームシナリオ**（`id: uuid`）— URLレベルでアクセスを受け、編集される単位。
- **ゲーム**（`id: uuid`）— ゲームシナリオが 1..* 個をコンポジション（実線ひし形）で保持。
  アクセス時に遊ばれ、編集される。
- **画像**（`id: uuid`, `url: str`）— ゲームが 0..2 個をアグリゲーション（白抜きひし形）で保持。
- **ブロック配置**（`id: Obj`）— ゲームが 1 個をコンポジションで保持。

メモ注記: 「ゲームシナリオはシナリオパラメータという属性を持ち、その中にゲームの順番を
定義している」。

このクラス図の XML は、ユーザーから提供された `<mxGraphModel>...</mxGraphModel>` という
中身だけの断片を、draw.io で開ける完全な形（`<mxfile><diagram>...</mxGraphModel></diagram></mxfile>`）
にラップして `doc_arch/diagrams/game-scenario-class-diagram.drawio` として保存し、`backend.md` から
リンクした。

## 2. 「DynamoDBで持つべきか」という問いへの回答

ユーザーからの質問: 「これってシナリオをキーにDynamoDBのようなKVオブジェクトで持った方が
いいのか？」

回答の要点:

- これは「アグリゲート単位（シナリオ丸ごと）でしか読み書きしない」典型的な KVS アクセス
  パターンであり、発想自体は正しい。
- ただしこの時点で既に `backend.md` には「MVPは DynamoDB を使わず Supabase の Postgres
  `jsonb` 列に持つ。Facade パターンで後から差し替え可能にしておく」という決定が先にあった。
- そのため、まずは「Postgres の `jsonb` 列に丸ごとJSONを持つ」という既存方針の延長で
  対応することを提案した（新規インフラを増やさない案を先に検討する、という順序）。

## 3. ユーザーによる方針確定：Supabase + DynamoDB ハイブリッド

ユーザーが以下のように方針を確定させ、「この時点で拡張しちゃっていいよ」と設計書への
反映を指示した。

> ユーザー情報は Supabase で持ってもいいが、ゲームに関する情報
> （シナリオ／ゲーム／画像参照／ブロック配置）は DynamoDB にする。

これを受けて `doc_arch/overview.md` / `doc_arch/backend.md` / `doc_arch/deploy.md` を更新した。

### 3.1 確定事項の整理（overview.md）

保存先を3系統に整理した。

| 系統 | 内容 |
|---|---|
| Supabase（Postgres + Auth） | Auth・ユーザー情報 |
| DynamoDB | ゲームデータ（シナリオ ID をパーティションキー） |
| Supabase Storage | 画像（変更なし、URL 参照のみ） |

### 3.2 DynamoDB 採用理由とテーブル設計（backend.md §2）

新設した「ゲームデータの保存先: DynamoDB」節に以下を記述した。

- **採用理由**: URL単位でシナリオ丸ごと取得するアクセスパターンが KVS 向きであること。
  ユーザー情報とはクエリ要件が異なるため、無理に Postgres へ一本化しない。
- **テーブル設計**: パーティションキー = `scenarioId`。シナリオに属する全ゲーム・画像参照・
  ブロック配置を**同一アイテム内にネストして丸ごと格納**する。個別ゲーム単位でのアクセスが
  将来必要になった場合は、別アイテムへの切り出しも可能という拡張余地を明記した。

### 3.3 データモデルの表現形式（backend.md §5.1）

クラス図の「ゲームシナリオ → ゲーム(1..*) → 画像(0..2) / ブロック配置(1)」という階層構造を、
そのまま DynamoDB の1アイテム内のネストした JSON 構造として書き直した（実体は
`doc_arch/schemas/game-scenario.schema.json`、詳細は
[[20260730_dynamodb-schema-as-design-doc-json-schema]] を参照）。

### 3.4 セキュリティ節への影響

Postgres 側の RLS（Row Level Security）はユーザー情報にのみ関係する仕組みであり、
DynamoDB 側には RLS 相当の仕組みが無い。そのため **DynamoDB 側の認可は API 層のコードのみで
担保する**という点を明記した。

### 3.5 ローカル開発環境への反映（deploy.md）

`amazon/dynamodb-local` をローカル構成に再度追加した。以前「DynamoDB採用は保留」として
一度ローカル構成から外していたが、採用決定に伴い復活させた。

## 4. 意図的にやらなかったこと：用語統一の一括対応は保留

既存の `requirements.md` / `frontend.md` は依然として「レベル」という単一階層の用語のままで、
新しい「シナリオ／ゲーム」という2階層の用語とはズレている。

このズレを**自動で一括リネームすることはしなかった**。代わりに `overview.md` の未決事項に
以下のように明記するだけに留めた。

> 用語の整理: requirements.md / frontend.md はまだ「レベル」という単位で書かれているが、
> backend.md のデータモデルは「シナリオ／ゲーム」という2階層に拡張済み。API契約・画面名・
> 要件記述の「レベル」を置き換えるかどうかは未反映。用語を揃えるタイミングで各ドキュメントに
> 反映すること。

**理由**: ユーザーから明示的に依頼されていない範囲まで独断で書き換えるのはスコープ超過。
用語統一はプロジェクト全体に影響する設計判断であり、ユーザー自身が決めるべき事項と判断した。

---

## 5. 教訓（一般化）

1. **KVS的な保存先の提案が来ても、既存の設計書に確定済みの方針があるなら、まずその延長線上の
   対応を検討してから新規インフラの導入を提案する。** 新規ミドルウェア（DynamoDB等）の追加は
   運用コストを伴うため、既存方針の範囲で解決できないかを先に検討する順序が安全。
2. ユーザーが明示的に「拡張していい」と述べた範囲だけを拡張し、**隣接する未確定領域（今回は
   `requirements.md` / `frontend.md` の用語）まで一括で手を広げない。** ズレは黙って残すのではなく、
   未決事項として明文化しておく。
3. クラス図のような外部インプット（draw.io の XML 断片等）は、そのままでは動作しない不完全な
   形で共有されることがある。開ける状態に補完してから成果物として保存する。
