# split-domain-module

`game_engine/src/*.rs`（`util` / `common` / `config` / `components` / `injection` / `systems`。
`systems`はさらに`setup`(Startup) / `update`(Updateスケジュール・observer) / `terminate`
(終端状態のOnEnter)に分かれる）が肥大化し、内部に複数の独立した関心事（ドメイン）が
同居してきたときに、それぞれを子モジュールへ切り出す「ファイル／モジュール分割」専用の
リファクタリング手順。

## スコープ

- **対象**: 1 つの `.rs` ファイルの中に、互いに独立した複数の関心事が同居している状態を、
  ファイル単位で分離すること。
- **対象外**: ECS のコンポーネント設計（`CLAUDE.md` の「役割ごとに型を分ける」「可変性・変更検知で
  分ける」という指針）、命名変更、ロジックの書き換え、DRY 化などの一般的なリファクタリング。
  これらは通常のコード変更として扱い、このスキルの手順は適用しない。

## いつ切り出すか（判断基準）

行数の絶対値では判断しない。**関心事が実際に混在しているか**で判断する。以下のサインが
複数当てはまるほど、切り出す根拠が強い。

1. ファイル内に互いに依存しない複数の関数グループがあり、それぞれが別々の
   component/resource/event の集合だけを使っている（＝ import の集合が自然に 2 グループ以上に
   分かれる）
2. ファイル冒頭のモジュール doc コメントが「〜と〜と〜を行う」のように複数の責務を列挙しないと
   説明できなくなっている
3. ある関心事だけを読みたい/テストしたいのに、無関係な関数を読み飛ばす必要がある
4. 兄弟のドメインが既に 1 つ切り出されている（例: `systems/collision.rs` が存在する）のに、
   他の関心事は親ファイルに残ったまま太り続けている

逆に、**切り出さない方がいい**場合:

- 対象がまだ数関数以下で、他の関心事と密結合している（同じ Component/Resource を頻繁に
  読み書きし合う）
- 1 関数だけを 1 ファイルにするような、機能単位ではなく関数単位の過剰な細分化

## 既存のトップレベルモジュール構成を尊重する（ただし実際の依存は必ず確認する）

`CLAUDE.md` に明記されたトップレベル構成（現状: `util` / `common` / `config` / `components` /
`injection` / `systems`）を、名前が似ている・意味が近いという印象だけで勝手に増減・統合しない。
ただし「尊重する」は「絶対に統合しない」という意味ではない。
**必ず `grep` で実際の呼び出し元を洗い出してから、モジュールの置き場所を決める。**

- 例: `systems::update` の当たり判定 4 関数 → `systems::update::collision`（親モジュール名と
  同じ名前のフォルダにサブモジュールとして退避する、素直なケース）。
- 例: かつてルート直下に独立モジュールとして存在した `notify.rs`（JS への通知実装）は、
  `grep` で洗い出した結果、呼び出し元が状態遷移時の通知 system 2 関数だけだと判明したため、
  最終的にその通知 system 側（現在は `systems::terminate`）へ統合した（非公開関数として
  同居させ、`collision.rs` が公開 system と非公開ヘルパーを同居させているのと同じ形にした）。
  「名前が同じだから」ではなく「唯一の呼び出し元が明らかになったから」統合したのがポイントで、
  印象や名前の一致だけで先に結論を出さないこと。

新しい関心事を切り出すべきか、既存モジュールに寄せるべきか、兄弟モジュールと名前が衝突/類似
するがどちらの立て付けにすべきか——これらは設計判断であり、正解が自明でないことがある。
判断に自信が持てない場合は、進める前に一言ユーザーに確認する。

## `util` / `common`（共通ヘルパー）に置くかどうかの判断基準

複数のファイルから呼ばれているロジックを見つけたとき、**呼び出し元の数だけを見て
共通モジュールに逃がしてはいけない**。まず対象の関数・型を呼んでいる箇所を全て
`grep` で洗い出し、その上で次の基準で `util` と `common` を使い分ける。

- **`util`**: ドメイン型（`components` の型など）に一切依存しない、純粋に汎用な計算・処理
  だけを置く。例: アスペクト比を保って内接させる `contain_fit`。ブロックにもパドルにも
  属さない純粋な座標計算で、ブロック用のテクスチャ切り出しと背景画像フィットという
  異なる 2 つの呼び出し元から使われている。
- **`common`**: ドメイン型には依存するが、単一のドメインモジュールの中に閉じずに複数箇所
  （例: `setup` と `systems` の両方）から共有される処理を置く。例: `spawn_brick` /
  `BrickAssets`（`Brick` という具体的なドメイン型を扱うが、初期配置の `setup` と
  再配置の `systems::reset_game` の双方から呼ばれる、ブロック生成の共有窓口）。
- 判断の軸は「ドメイン型に依存するかどうか」（→ `util` か `common` か）であって、
  「呼び出し元がいくつあるか」ではない。呼び出し元が 1 箇所しか無いドメイン固有の処理は、
  どちらにも置かず、そのドメインの既存モジュール内に留める。
- **`common` に `Query` を引数に取る関数（＝ Bevy のスケジューラが直接呼ぶ system）を
  置いてはいけない。** `common` は「他の system や setup から普通の関数として手動で
  呼ばれるヘルパー」の置き場であり、Bevy が自動実行する system・observer とは役割も
  呼び出され方も違う。`Query` を取る関数を見つけたら、それがどれだけドメイン型に依存していて
  何箇所から使われていようと、必ず `systems`（`systems::update` 等）側に置く。
  例: 破れたブロックを再描画する `redraw_broken_bricks` は `Brick` に依存し `common` 側の
  `spawn_brick` とも関連が深いが、`Query<...>` を取り `main` の `add_systems(Update, ...)` に
  直接登録される system なので `systems::update::brick` に置き、`common` 側は
  `build_brick_mesh` を `pub(crate)` で公開するだけに留めている。

## 手順

1. 対象ファイル（例: `game_engine/src/systems.rs`）を読み、切り出す関心事に属する関数・型・
   import をリストアップする。
2. まだ `<親名>/` フォルダが無ければ作成する（例: `game_engine/src/systems/`）。フォルダ名は
   親ファイル名（拡張子抜き）と揃える。
3. `<親名>/<ドメイン名>.rs` を新規作成し、対象の関数・型を移す。
   - ファイル冒頭に、何を切り出したモジュールかを一言で説明する doc コメント（`//!`）を書く
     （既存の `systems/collision.rs` の書き出しを参考にする）。
   - import は対象コードが実際に使うものだけを持たせる。親ファイルの import 一覧を丸ごと
     コピーしない。
4. 親ファイル（例: `systems.rs`）側を編集する。
   - 冒頭に `mod <ドメイン名>;` を追加する。
   - `pub use <ドメイン名>::{関数名, ...};` で再エクスポートし、外部（`main.rs` など）からの
     アクセスパス（`systems::関数名`）を変えない。
   - 移動した関数の実体と、それだけが使っていた import を親ファイルから削除する。
   - 親ファイル冒頭のモジュール doc コメントを、子モジュールの存在と依存の向き（親は子を読むが
     子は親を読まない／呼び出し側は親モジュール経由でのみアクセスする）が伝わるように更新する。
5. `main.rs` など呼び出し側は、通常は親モジュール経由の import（`systems::{...}`）のままで
   変更不要。パスが変わっていないことだけ確認する。
6. `CLAUDE.md` のビルド規約に従い、順に確認する。
   - rust-analyzer / `cargo check --target wasm32-unknown-unknown`（**加えて** wasm32 を付けない
     素の `cargo check` も実行し、ネイティブ側だけの警告が無いか見る）でエラー・警告 0 を確認する。
     `#[cfg(not(target_arch = "wasm32"))]` を含む関数を切り出した場合、その関数専用の import が
     wasm32 側でだけ未使用になり警告が出ることがある。その import 自体にも同じ `#[cfg(...)]` を
     付けて解決する。
   - `cd frontend && pnpm build:wasm` で WASM 再ビルド。
   - Playwright MCP で実ブラウザ描画確認（スクリーンショット・コンソールログ・`window` グローバル
     の 3 点で確証を取る）。
7. 親ファイル末尾に `#[cfg(test)] mod tests` がある場合、移動対象の関数に対するテストであれば
   一緒に子モジュールへ移す。それ以外のテストは親ファイルに残す。

## 完了報告

切り出したファイルパス、親ファイルの変更点（`mod` / `pub use` の追加、削除した import）、
ビルド確認（rust-analyzer / cargo check / wasm ビルド / Playwright）の結果を簡潔にまとめて
報告する。
